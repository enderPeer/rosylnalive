# ADR R5-0001: In-box WARP runs the D3D12 path as d3d12-warp; a d3d12-warp CI job is viable once the runner is measured

- **Status:** proposed (R5, 2026-10-18), with the R5 pull request.
- **Owner:** R5.
- **Scope:**
  - in-box WARP as the `d3d12-warp` ExecutionClass: device, shader model, binding model, fp32 denormals and NaN;
  - D1's selftests and E1's conformance harness on it;
  - the proposed optional `d3d12-warp` CI job;
  - the Agility SDK half of R5, which is skipped.
- **Code:** `spikes/d3d12/` (throwaway; not built in CI, ProjectGraph contract).

## Context

GitHub-hosted runners have no GPU, so CI runs only the cpu tier, and every D3D12 check runs on the development machine alone. Windows ships a software rasterizer, WARP (the Microsoft Basic Render Driver). If it runs LRM's D3D12 path, a CI job could run D1's backend and E1's harness on every pull request. The plan lists that job as optional, "only after R5" (dev plan, section 7).

The open questions:

- whether in-box WARP supports shader model 6.6 with a directly indexed resource heap (the plan's risk table lists "WARP SM 6.6" as unverified);
- whether D1's backend runs on it without changes;
- which fp32 denormal mode it has (ADR int-0001 has D3D12 hardware as `preserve`);
- whether the runner image has the same WARP.

Constraints:

- R3's device check rejects WARP for `d3d12` on purpose, because `d3d12-warp` is its own class (D3D12ComIdiom, "Device check"). D1's ADR names what a `d3d12-warp` backend needs: "a provider that enumerates the software adapter and a class with `Backend = D3D12Warp`".
- R5 owns only `spikes/d3d12/**` and this ADR, so D1's code is used as it is.
- AP-4 (the Agility SDK NuGet) is not approved, and nothing may be downloaded.
- Agents may not edit `ci.yml` or poll CI, so the runner image is not measured here.

## Decision

1. **WARP is a working `d3d12-warp` device.** In-box WARP 10.0.26100.9711 has every requirement on the development machine: shader model 6.8, resource binding tier 3, and a root signature with `CBV_SRV_UAV_HEAP_DIRECTLY_INDEXED`. Its compute pipelines are built from the embedded `cs_6_6` DXIL blobs, which index `ResourceDescriptorHeap`. LRM's D3D12 path (the heap of 64 raw UAVs written once, the 1 MiB tensor table, 32 root constants at b0, timestamps, copies through the scratch buffer) runs on it unchanged.
2. **The d3d12-warp device rule** is the d3d12 rule with the hardware clause inverted:
   - a software adapter with Microsoft's vendor id 0x1414;
   - a device at feature level 11_0;
   - shader model 6.6 or later;
   - resource binding tier 3.

   The adapter comes from `IDXGIFactory4::EnumWarpAdapter`. Its LUID is the software adapter's LUID in D1's enumeration (`EnumAdapterByGpuPreference`, high performance, index 1 here), so `D3D12Backend.Create` opens it with the d3d12 DeviceInfo of that index.
3. **The class is `d3d12-warp`**, filled by `GpuClass.fill` from a DeviceInfo with `Backend = D3D12Warp`:
   - `DeviceId` is `pci:1414:008c`;
   - `Driver` is WARP's user-mode version (10.0.26100.9711), so every WARP build is its own class;
   - `Arch` keeps the CPU feature flags (`win-x64+avx2+fma` here), so a runner's CPU is its own class too;
   - `ShaderSetHash` is the DXIL set's.

   A CI WARP class therefore never shares a bit-identity claim with a local one. CI checks run-twice within its run, and KernelBounds against CpuRef.
4. **fp32 denormals on WARP are `preserve` with the shader set's `-denorm preserve`, and `flush` without the flag**, exactly as on the RTX 4080 (int-0001). The flag decides the mode on both D3D12 devices measured. The d3d12-warp class records `preserve`.
5. **NaN results on WARP keep the CPU's payload.** For `scale_f32`, WARP's words equal CpuRef F32's in every bit, NaN payloads included: the first NaN operand with its quiet bit set. The RTX 4080 returns `7fffffff` for every NaN (R1 pitfall 10). KernelBounds' "any NaN matches any NaN" rule for `scale_f32` and `add` covers both. Every other selftest word is the same on WARP and on the RTX 4080.
6. **A `d3d12-warp` CI job on windows-latest is viable, as an optional job, once one runner run confirms the image's WARP.** The job proposed below is the target. Its condition: the one-off run must show the d3d12-warp verdict ACCEPTED and the tiers green on the runner image. The development machine's WARP (10.0.26100.9711) passes everything in about 4 s at 4 processors. The runner image's WARP is unmeasured (Evidence, "Not measured").
7. **On d3d12-warp the 100 ms dispatch budget should not gate, and GPU-only cases should not run in CI.** At 4 processors WARP moves about 2 GB/s in `scale_f32` (3.5 to 4 ns per element). The budget would fail at about 25 M elements at 4 processors and at about 11 M at 2. For example, a decode step's lm_head reads 311 MB of bf16 weights; at the measured rate that alone takes about 150 ms on a runner, before any arithmetic (an estimate: K2's kernel does not exist yet). The budget exists for a GPU's timeout detection, and WARP runs in the process on the CPU, without one. WARP's times measure the runner's CPU, not a GPU. This is a request to E1 and the integrator: the ConformanceHarness would treat `d3d12-warp` as it treats `cpu-device` (`budget_gating` false, `GpuOnly` cases skipped).
8. **The Agility SDK half is skipped:** AP-4 is not approved. The in-box runtime (D3D12Core 10.0.26100.9549, SDK version 616) already gives SM 6.8 and enhanced barriers on this machine, so Phase 1 needs no Agility SDK here.

**Tests.** The spike's gpu tier ran under the d3d12 mutex at 4 logical processors (`LRM_WARP_CPUS`, default 4). Result: 39 passed, 26 skipped, 0 failed, in 3.4 s. Commands: `pwsh spikes/d3d12/ci-probe.ps1` with `LRM_WARP_CPUS=4`, at commit `ddd32a7`. The runs and their reports:

- run `20261018-064937-ce781a73`: [`reports/warp-selftests/kernels.md`](../../spikes/d3d12/reports/warp-selftests/kernels.md);
- run `20261018-064940-3cfef694`: [`reports/warp-conformance/kernels.md`](../../spikes/d3d12/reports/warp-conformance/kernels.md).

What the tier showed:

- **The adapter and the backend.** The adapter facts are those above. D1's `D3D12Backend.Create` opens the WARP adapter, and the wrapper names the class `d3d12-warp`. No D1 code changed.
- **The probe.** D1's probe in `LoadKernels`, on the embedded `scale_f32` (`-T cs_6_6 -E main -HV 2021 -O3 -WX -denorm preserve`), gives `preserve`: `3f000000 00800000 00400000 80400000 00000001 803fffff 00200000`. The words are bit-identical twice, on two backends.
- **The control.** The int-0001 control is `scale_f32.hlsl` compiled at test time with the pinned DXC and the same flags without `-denorm`, swapped into a copy of the set. It gives `flush`: `3f000000 00800000 00000000 80000000 00000000 80000000 00000000`, twice. The selftests report shows both measurements next to the RTX 4080's, in its bit table.
- **D1's five selftests (nine cases)** are bit-exact against the CPU and `KernelBounds.checkExact`, and bit-identical across two runs. Every dispatch is under 100 ms. The negative control leaves every element of every case unwritten.
  - The slowest dispatch is `groups_echo` at 131,077 groups (folded to 43,693 × 3): 12.7 to 15.6 ms.
  - A submission of the nine dispatches takes 13.0 to 14.5 ms of WARP time.
- **WARP against the RTX 4080** (the same selftests on both, word for word; driver 616.92):
  - Eight of the nine cases have the same bits.
  - `scale_f32` x→y differs in 17 of 4,099 words, all NaN. The RTX 4080 returns `7fffffff` for each of them. WARP returns 18 distinct NaN words, such as `7fc00001` for the signalling NaN `7f800001` and `ffc00001` for `ffc00001`.
  - Against the CPU's expected words in every bit, WARP differs in 0 words and the RTX 4080 in 17.
- **D1's copy test** passes on WARP: a copy across pages and two within a page through the scratch buffer, each intermediate checked. **Descriptor writes** are 64 at `CreateHeap` plus 64 on the probe's transient heap, then none. **COM references** are all released.
- **E1's conformance suite** on d3d12-warp passes all 28 cases: `scale_f32` 11, `bf16_unpack` 5, `groups_echo` 6, `table_echo` 4 and `args_echo` 2.
  - Each case is run twice, region-checked and batch-split, against the probe's `preserve` mode.
  - The 110 dispatches take 91 ms of WARP time, the slowest 14.6 ms. `time_source` is `gpu` and `budget_gating` is true.
  - The negative control fails every case, as it must.
  - 26 cases are skipped: the `e1_` cases of K1 to K3, whose kernels have no source yet.
  - E1's D3D12 preview report has the same 28 cases passing on the RTX 4080.

**Throughput and the budget.** `scale_f32` is dispatched alone with timestamps over n elements, x to y, 8 bytes moved per element, twice in each run. Each result is exact against the CPU. The runs at 2 and 8 processors (commit `8051ad6`, the same throughput code) render to:

**Cost of the job, measured locally:**

- A clean build of the spike and its references (`dotnet build spikes/d3d12/WarpSpike.fsproj -c Release -m:4` into an empty artifacts folder) takes 22 s. With the CLI, through `ci-probe.ps1`, it takes 34.5 s.
- The cpu tier takes 0.4 to 0.6 s and the gpu tier 3.2 to 3.9 s.
- No step downloads anything beyond the build-test job's restore and the DXC bootstrap.

**Not measured:**

- **The windows-latest image.** windows-latest is assumed to be Windows Server 2025, build 26100 (GitHub moved the label in 2025; not re-checked in this session). That build ships the 10.0.26100 WARP line, so shader model 6.6 and tier 3 are likely but unverified. Server 2022's WARP (build 20348) is unknown here, and a `windows-2022` pin would need its own measurement.
- **The runner's processor count.** It is 4 for a public repository (`gh repo view` reports this repository public), but unverified on the runner.
- **Debug-layer validation.** D3D12SDKLayers is not installed here, so the debug layer did not validate WARP runs. WARP runs only with the in-box runtime's own checks.

## The proposed job

It is optional, not a required check. It goes in `ci.yml` beside build-test, on the same triggers. Its first run is the one-off measurement:

- The integrator adds it on an `int/` branch with `continue-on-error: true`. Its pull-request run is the measurement. A `workflow_dispatch` of a new workflow file does not work until that file is on the default branch.
- If `warp-info` reports ACCEPTED and both tiers pass, the flag is dropped.
- If it reports REJECTED (exit 3), the job is removed and this ADR is superseded with the runner's facts.

```yaml
  # R5 (ADR R5-0001): D3D12 on in-box WARP, the only D3D12 device a runner has. Optional, not a required check.
  d3d12-warp:
    runs-on: windows-latest
    timeout-minutes: 20
    defaults:
      run:
        shell: pwsh
    env:
      LRM_WARP_CPUS: all
    steps:
      - uses: actions/checkout@v5
      - uses: actions/setup-dotnet@v5
        with:
          global-json-file: global.json
      - name: Use a temporary LRM_DATA
        run: |
          $root = Join-Path $env:RUNNER_TEMP 'lrm-data'
          New-Item -ItemType Directory -Force -Path $root | Out-Null
          "LRM_DATA=$root" | Out-File -FilePath $env:GITHUB_ENV -Append -Encoding utf8
      - name: Cache NuGet packages
        uses: actions/cache@v4
        with:
          path: ~/.nuget/packages
          key: nuget-${{ runner.os }}-${{ hashFiles('global.json', 'Directory.Packages.props', 'build/locks/*.json', '.config/dotnet-tools.json') }}
      - name: Cache toolchain
        uses: actions/cache@v4
        with:
          path: ${{ env.LRM_DATA }}/toolchain
          key: toolchain-${{ runner.os }}-${{ hashFiles('tools/bootstrap/toolchain.json') }}
      - name: Bootstrap (DXC download allowed on runners, AP-1)
        run: ./tools/bootstrap/bootstrap.ps1 -AllowDownload
      # Interim (the one-off measurement): the R5 spike. Final: the d3d12-warp provider and test groups, below.
      - name: WARP device, D1's selftests and E1's conformance on d3d12-warp
        run: ./spikes/d3d12/ci-probe.ps1 -Results artifacts/warp-ci
      - name: Upload WARP results
        if: always()
        uses: actions/upload-artifact@v4
        with:
          name: d3d12-warp
          path: artifacts/warp-ci/
          if-no-files-found: ignore
```

**The interim step builds a spike, and `spikes/**` is never built in CI** (ProjectGraph). It is acceptable for the one-off measurement only. The permanent job replaces that step with `./tools/test.ps1 -Tier gpu -Project Lrm.Gpu.D3D12.Tests,Lrm.Kernels.Conformance` and `LRM_BACKENDS=d3d12-warp` once these exist:

1. **D1:** a `d3d12-warp` provider in `Lrm.Gpu.D3D12`. It would enumerate `EnumWarpAdapter`'s adapter under the rule of decision 2, and the backend would take its `ExecutionBackend` from the DeviceInfo instead of the fixed `D3D12` in its telemetry, its probe record and its class. `spikes/d3d12/src/WarpBackend.fs` and `Relabel.fs` are the prototype; the encoder, heap, probe and selftests are reused as they are, as D1's ADR expected.
2. **S0:** a `d3d12-warp` backend in Lrm.Testing (`Backend`, `LRM_BACKENDS`, `LRM_REQUIRED_BACKENDS`, `tools/test.ps1`'s backend list). It needs either its own mutex or the d3d12 one; the spike takes the d3d12 mutex.
3. **E1:** `Suites.gpuWith` gets d3d12-warp, under decision 7's rules.

## Consequences

- **The integrator:**
  - adds the optional job on an `int/` branch for the one-off measurement, and records the runner's `summary.md` (OS build, WARP version, verdict, tier results) in STATUS;
  - adds R5-0001 to the index in `0000-adr-process.md`;
  - decides the d3d12-warp mutex and backend name in Lrm.Testing (S0).
- **D1:** a d3d12-warp provider (above). Until then, D1's records on WARP say `backend = d3d12`, and only the spike's relabelling makes them `d3d12-warp`.
- **E1:** with that provider, the gpu tier runs the harness on d3d12-warp. Its budget does not gate there, and `GpuOnly` cases skip (decision 7). On WARP, `scale_f32` and `add` keep CPU NaN payloads, so the class-dependent NaN rule is needed only for hardware.
- **K1 to K3:** a kernel that passes on d3d12-warp in CI has passed DXIL compilation, the runtime's PSO validation and KernelBounds on a real D3D12 runtime, before any GPU run. Kernel timing on WARP says nothing about the 100 ms budget on a GPU.
- **Reopen** this decision if:
  - the runner's WARP is rejected or differs in mode or NaN behaviour;
  - a Windows update changes `d3d10warp.dll` and its probe;
  - AP-4 or AP-7 is approved (an Agility SDK or the WARP NuGet would replace the in-box runtime).

## Alternatives

- **A thin spike backend instead of D1's backend.** Rejected: D1's `Create` already opens any enumerated adapter, so the spike tests D1's code itself, which is what the CI job would run.
- **Accept WARP in the d3d12 class.** Rejected: WARP runs on the CPU, and its bits (NaN payloads) and times differ from hardware, so the classes must stay separate (R3, ExecutionClass).
- **The Agility SDK (AP-4) or the WARP NuGet (AP-7)** for a newer runtime or WARP than the image ships. Not needed while the in-box parts suffice, and not approved. A process started as `dotnet <dll>` also cannot use the Agility SDK's export-based opt-in (`D3D12SDKVersion` in the host exe), so it would need the runtime's `ID3D12SDKConfiguration` path. That path is unverified here.
- **Gate CI on the 100 ms budget on WARP.** Rejected (decision 7): the budget would measure the runner's CPU.
- **Run WARP unpinned on the development machine.** Rejected: WARP takes every logical processor, which the other agents share. The spike pins only its own process (`LRM_WARP_CPUS`) and changes no system setting.
