# ADR V1-0001: The Vulkan backend: the recipe as built, its barriers, and what it measured

- **Status:** proposed (V1, 2026-10-18), with the V1 pull request.
- **Owner:** V1.
- **Scope:** `src/Lrm.Gpu.Vulkan` (the `vulkan` backend of GpuBackendInterface) and the facts the executor (X1), the conformance harness (E1), KernelBounds (O2) and the gates build on.
- **Builds on:** VulkanHeapRecipe v1.1 ([R1-heap-recipe.md](R1-heap-recipe.md)), R2's interop ([R2-0001](R2-0001-vkgen-and-vulkan-interop.md)), D1's backend ([D1-0001](D1-0001-d3d12-backend.md)), whose structure, tests and telemetry V1 mirrors.

## Context

VulkanHeapRecipe fixes the binding path: one resource heap written once, a set 0 binding 0 → heap mapping with `HEAP_WITH_CONSTANT_OFFSET`, heap pipelines with a NULL layout, the 128-byte ArgBlock as push data, and synchronization2. GpuBackendInterface fixes what a backend does, the same for D3D12, Vulkan and CpuDevice. What was left open: how the recipe meets the interface's barrier and copy semantics, how submissions see each other, how memory and the heap are laid out from the queried limits, what device loss reports, and what the Vulkan class measures. D1 answered the same questions for D3D12; V1 follows D1 wherever Vulkan allows, so the two backends behave alike through the interface.

## Decision

1. **The recipe's device, through R2's interop.** `Device.create` with `DeviceOptions.diagnostics`: Vulkan 1.4, `VK_EXT_descriptor_heap` and the recipe's five features over R2's `FeatureChain`, plus `VK_EXT_device_fault` (with `deviceFault`) and `VK_EXT_memory_budget` where the device supports them. Device fault is the one addition beyond the recipe's single extension, for the diagnostics GpuBackendInterface asks of Vulkan (R2's open point). One queue of the recipe's family (the first with COMPUTE, without GRAPHICS, with timestamps: family 2) and one timeline semaphore per backend. The instance enables `VK_EXT_debug_utils` when the loader offers it, and `DeviceOptions.Debug` adds `VK_LAYER_KHRONOS_validation` when it is installed (AP-3 is not approved; it is not installed). `VulkanBackend.Create` checks that the device index still has the enumerated device's UUID and that DeviceCheck accepts it.
2. **Discovery and rejection texts.** `PhysicalDevices.enumerate` maps R2's `DeviceCheck` reports to `DeviceInfo` (Driver = `GpuClass.vulkanDriver driverInfo driverVersion`, `616.92`; details include the queue family, the heap limits and the memory types). The three requirements GpuBackendInterface names use its `Requirements` texts (`VK_EXT_descriptor_heap`, buffer descriptors of at most 16 bytes, 128 bytes of push data); every other reason is DeviceCheck's, so the device check and the backend reject the same devices.
3. **Memory types by flags, recorded.** Each buffer's type is the first among its `memoryTypeBits` that matches the first matching tier of required and forbidden flags (`MemoryTypes.tiers`): pages DEVICE_LOCAL without HOST_VISIBLE; the heap DEVICE_LOCAL | HOST_VISIBLE | HOST_COHERENT; upload staging HOST_VISIBLE | HOST_COHERENT preferably neither HOST_CACHED nor DEVICE_LOCAL; readback staging HOST_CACHED when a type has it. LAZILY_ALLOCATED and PROTECTED memory is never used. The first choice of each kind is a `gpu.memory_type` event, and the gpu tier writes the choices into the run manifest. Every buffer has its own allocation; buffers with device addresses allocate with `VK_MEMORY_ALLOCATE_DEVICE_ADDRESS_BIT`.
4. **The heap.** `Heap.vulkanGeometry` over the queried limits (R4b), never the stride-16 helpers. The heap buffer is `heapRange.size` plus one `resourceHeapAlignment` of slack, and `heapRange.address` is its address aligned up. All 64 slots are written in one `vkWriteResourceDescriptorsEXT` call, slot *i* at byte *i* × `bufferDescriptorSize`: slot 0 the 1 MiB table, slots 1..N the pages, the rest a 64 KiB dummy page (no null descriptors without robustness2). Page addresses are checked against `minStorageBufferOffsetAlignment`. The backend never reads or writes the reserved range, and before it destroys a heap it waits for and resets every command pool, so no command buffer still holds a binding (recipe section 4, pitfall 13).
5. **Pipelines.** Every SPIR-V blob is first checked by R4b's `SpirvInspector` (its `gpu.shader.*` records go to the run log), then by a V1 guard: a whole number of words whose last instruction is `OpFunctionEnd` (finding 2). A blob that fails is an `ArgumentException`, as D1's non-canonical `rootsig.bin` is, because no interface rule covers it. The pipeline carries `VK_PIPELINE_CREATE_2_DESCRIPTOR_HEAP_BIT_EXT`, a NULL layout and `HeapMapping.create bufferDescriptorSize`, built from R4b's `SpirvBinding` values (its 96 bytes are KAT-1). The shader module is destroyed once the pipeline exists.
6. **A pure encoder.** As in D1, a command list records commands checked with RecordingBackend's checks and texts (`Dispatch.prepare`, `checkCopy`, `checkTransfer`, unchanged), and `Plan.encode` turns them into native ops at `Submit`; `Plan.verify` checks an encoding, in the cpu tier on known answers and random lists, and on every submission with `DeviceOptions.Debug`.
   - A list that dispatches binds the heap once (`vkCmdBindResourceHeapEXT`) before its first dispatch. A dispatch binds the pipeline when the kernel changes and always pushes its own 128-byte ArgBlock at offset 0 (`vkCmdPushDataEXT`), so push data follows every pipeline bind.
   - **`Barrier ()` is the recipe's dispatch barrier** (section 6.3: COMPUTE / SHADER_STORAGE_WRITE before COMPUTE | COPY / SHADER_STORAGE_READ | SHADER_STORAGE_WRITE | TRANSFER_READ), recorded where the interface asks for a barrier, between dependent dispatches, not after every dispatch. Section 6.3 says "after each dispatch"; GpuBackendInterface lets independent dispatches overlap, the executor inserts a barrier before every dependent dispatch, and D1 adds none either, so both backends serialize exactly where the caller asks. This is the one place where V1 reads the recipe through the interface (request 4).
   - **Every list that dispatches or copies starts with a `ListStart` barrier** (COMPUTE | COPY writes before COMPUTE | COPY reads and writes). Vulkan gives no memory dependency between submissions on one queue, while a D3D12 list sees everything the queue ran before it; with this barrier a Vulkan list does too, including the backend's own upload lists.
   - **`Copy` is a full barrier:** `BeforeCopy`, `vkCmdCopyBuffer`, `AfterCopy`. A copy within one page is one `vkCmdCopyBuffer` with the same buffer as source and destination, which Vulkan allows for non-overlapping regions (`checkCopy` refuses overlap), so V1 needs no scratch buffer (D1 does).
   - Uploads end with the recipe's upload barrier and downloads with its host barrier (COPY / TRANSFER_WRITE before HOST / HOST_READ); the host reads the HOST_CACHED | HOST_COHERENT readback memory after the timeline wait.
7. **Timing.** Timers and, with `TimeDispatches`, every dispatch are bracketed by `vkCmdWriteTimestamp2(ALL_COMMANDS)`, masked to `timestampValidBits` and scaled by `timestampPeriod`. A timed dispatch is preceded by a `Serialize` barrier (an execution dependency), so its interval covers it alone, as D1's UAV barriers do. Without `TimeDispatches` nothing is added. Timers are emitted once, at the first `Wait`, as in D1.
8. **Submissions and frames.** `Submission` values count the caller's submissions (1, 2, 3, ...); the timeline also counts the backend's transfer and probe lists. A frame (a transient command pool, its command buffer and a timestamp query pool) is reused only after its timeline value has completed, and its pool is reset before it records again. The backend keeps what `Wait` needs and no more, with D1's layout: 4 bytes per submission, a few hundred per submission timer, 24 per timed dispatch.
9. **Device loss.** `vkQueueSubmit2`, the timeline wait and the counter query map `VK_ERROR_DEVICE_LOST` to `VulkanDeviceLostException`, which carries the call, the result and `vkGetDeviceFaultInfoEXT`'s report (R2's `DeviceFault.query`). A wait that does not finish within 30 s raises the same exception with `VK_TIMEOUT`. A failed submit takes back its timeline value, so teardown does not wait for a value that was never signalled. It is not a contract violation. Every buffer, memory, pool, query pool, pipeline, the semaphore and the queue carry `lrm.vulkan.*` debug names.
10. **The fp32 denormal probe** runs inside `LoadKernels` on a transient private heap, exactly as in D1 (its own 64 descriptor writes, counted in `ProbeDescriptorWrites`; the `gpu.probe` span; `gpu.buffer_memory` for `probe_heap`). The mode is `VulkanBackend.Fp32Denormals`, recorded with `Fp32Denormals.recordProbe` and in the gpu tier's run manifest (`fp32_denormals`). The ExecutionClass record has no field for it; it is a measured property of the class, as GpuBackendInterface states.
11. **The recipe's fallback heap placement is built and tested:** `HeapPlacement.Copied` (DEVICE_LOCAL, descriptors written to host staging, one `vkCmdCopyBuffer`, then COPY / TRANSFER_WRITE before COMPUTE / `RESOURCE_HEAP_READ`). It is used on a device without a DEVICE_LOCAL | HOST_VISIBLE type, and a test forces it on the RTX 4080.
12. **The selftests are D1's module, copied.** A library may not reference another backend (ProjectGraph), so `Lrm.Gpu.Vulkan.SelfTests` is `Lrm.Gpu.D3D12.SelfTests` line for line, with D1's seed and stream names. The cpu tier checks that the inputs, the layout, the table image, the expectations and the poison are the same bytes, which is what makes the cross-backend comparison meaningful (request 2: move it to `Lrm.Gpu.Core`).
13. **`hello-vulkan`** is `Hello.run shaders args` in the library; the test exe's `hello-vulkan` entry point runs it under the vulkan mutex. A CLI command is one line for the integrator.

## Evidence

The development machine: NVIDIA GeForce RTX 4080 (`pci:10de:2704`), Vulkan 1.4.351, driver 616.92, Windows 11 10.0.26200. On `ws/V1-vulkan` the SPIR-V ShaderSetHash is `a1a15c99c3fb545f908085c72e58afeeca4563dee6e546eca0e359d4c06064c9` and the ExecutionClass id `9c41399f5fa994e5e281b10f2302d50acba455e94fbbe2ef4aa0f78e7870a928`. Run `20261018-155431-a38f1165` (the gpu tier, commit `d6493b7`) renders to [`selftests/kernels.md`](../../tests/Lrm.Gpu.Vulkan.Tests/reports/selftests/kernels.md) and [`selftests/inference.md`](../../tests/Lrm.Gpu.Vulkan.Tests/reports/selftests/inference.md); run `20261018-154101-9eb7a6c2` (conformance with K1 to K3) to [`conformance/kernels.md`](../../tests/Lrm.Gpu.Vulkan.Tests/reports/conformance/kernels.md).

- **Device:** queue family 2, 64 timestamp bits at 1 ns per tick; extensions `VK_EXT_descriptor_heap`, `VK_EXT_device_fault`, `VK_EXT_memory_budget`; debug names on; no validation layer. On a healthy device the fault query answers `VK_ERROR_UNKNOWN` (no fault to describe), as R2 found, and never raises.
- **Memory types** (by flags): pages 1 (DEVICE_LOCAL), heap 4 (DEVICE_LOCAL | HOST_VISIBLE | HOST_COHERENT), upload 2 (HOST_VISIBLE | HOST_COHERENT), readback 3 (HOST_VISIBLE | HOST_COHERENT | HOST_CACHED): R1's ADR's values.
- **Heap:** in place, `heapRange` 97,792 bytes at a 64-aligned address, 64 slots of 16 bytes in 1,024, reserved range 1,024 + 96,768 (KAT-2). 64 descriptor writes at `CreateHeap`, each into its slot and none into the reserved range, 64 on the probe's transient heap, and none afterwards through `WriteTable`, a dispatch, a copy, an upload and a download. The slot area's 1,024 bytes are unchanged after that work, and the heap never moves.
- **Probe:** `flush`, `3f000000 00800000 00000000 80000000 00000000 80000000 00000000`, the same in every run (int-0001's expectation; the addendum records it).
- **Selftests:** the nine cases of the five selftests are bit-exact against the CPU in flush mode and against `KernelBounds.checkExact`, bit-identical across two runs, and the negative control fails every case as unwritten. Every NaN result of `scale_f32` is `0x7FFFFFFF`, as on D3D12. E1's CpuDevice in the class's model (flush, canonical NaN) gives the same bytes, case by case.
- **Across backends:** against D3D12's run of D1's suite in the same process (preserve), 201,365 words are identical. The 27 `scale_f32` elements with a denormal input or a tiny product are class-only; none of the compared words differs.
- **Contract errors:** the 48-step script of valid and invalid calls gives exactly RecordingBackend's outcomes, type and text, step by step (as D1). After `Dispose` every call raises `ObjectDisposedException`, also on a list begun before it. A blob with a zeroed magic number (the inspector) and one truncated by its `OpFunctionEnd` (the guard) raise `ArgumentException` and leave no Vulkan object behind; `LoadKernels` then succeeds with the embedded set.
- **Copied heap:** the selftests give the in-place heap's bits.
- **Copies:** dispatch → copy across pages → dispatch → copy within a page → dispatch → copy within a page, in one list, gives the CPU's values for every intermediate. A whole 1 GiB page is one storage-buffer descriptor, read and written at bytes 0, 512 MiB + 64 KiB and 1 GiB − 64 KiB.
- **Round trip:** `model.safetensors` of Qwen3-0.6B (1,503,300,328 bytes, two Weights pages) goes up with `UploadFrom` and comes back with its SHA-256 (`SHA256SUMS`), twice per run: upload 0.27 to 0.49 s (3.0 to 5.6 GB/s, the file in the page cache), download 0.75 to 0.93 s (1.6 to 2.0 GB/s, SHA-256 on the host).
- **Soak:** 10,000 dependent `scale_f32` dispatches, twice in each of D1's three modes, exact. The frame pool stays at 1, live Vulkan objects at 26 (25 without timers: no query pool), nothing pending after the last `Wait`. GPU time per timed dispatch 1.0 to 2.0 µs depending on the clock state, 137 to 157 µs per timed submission of 100; host time per submission 0.47 to 0.71 ms timed, 0.31 to 0.45 ms with a submission timer, 0.07 to 0.11 ms without timers. Managed memory kept per dispatch (Theil–Sen over ten samples after full collections) 14.7 to 26.0 bytes timed (bound 48), 2.5 to 2.9 with a submission timer and 0.54 without timers (bound 16): D1's layout.
- **Objects:** the process-wide Vulkan object count is the same before a backend is created and after it is disposed.
- **Conformance** (E1's harness, discovered through `Vulkan.provider`): on this branch 27 of the 28 selftest cases and the negative control pass; on a local merge with `main` (K1 to K3), 213 of 214 cases and the negative control pass, every K1 to K3 kernel included, and every dispatch is under the 100 ms budget. The failing case is finding 1.

## Findings

1. **The flush class detects tininess before rounding.** The probe's seven inputs cannot tell whether a flushed result is judged before or after rounding. Products at the bottom of the normal range can: `0x00FFFFFF * 0.5` is exactly 2^-126 × (1 − 2^-24), which IEEE rounds up to the smallest normal `0x00800000`, and the Vulkan class returns 0 (`0x80FFFFFF` gives −0). D3D12, in preserve, returns the IEEE bits. The gpu test "the flush class flushes products below 2^-126 before rounding" measures eight such inputs twice and records them as `gpu.fp32_tininess`. The model is: a denormal input, or a non-zero exact product below 2^-126, gives zero of the product's sign. `Fp32Denormals.flushBits` composed after the multiply (round, then flush), and the harness's flush-mode CpuRef, predict the smallest normal there, so E1's gating case `scale_f32/denormals` fails on Vulkan at element 11. Adds cannot hit this (an exact sum below 2^-126 is representable), and kernels with relative bounds absorb it through the 2^-126 allowance. Request 1; the int-0001 addendum records it.
2. **R4b's inspector accepts a truncated module, and the driver hangs on it.** A `scale_f32` blob without its final `OpFunctionEnd` (or without `OpReturn` and `OpFunctionEnd`) passes `SpirvInspector.inspect` with no finding. NVIDIA 616.92 then did not return from pipeline creation for more than ten minutes, until the process was killed (the GPU recovered). V1's guard now refuses such a blob before `vkCreateShaderModule`; the inspector should too (request 5).
3. **The recipe's "after each dispatch" barrier** (section 6.3) is applied where the interface asks for a barrier (decision 6). Every gpu-tier and conformance case passes with that reading, D1 makes the same choice, and the executor inserts a barrier before every dependent dispatch.

## Consequences

- **X1:** the two backends have the same barrier and copy semantics through the interface. A Vulkan copy costs two barriers and one `vkCmdCopyBuffer`, also within one page; every list that dispatches or copies starts with one barrier more than D3D12 needs.
- **E1 and O2:** bit-exact fp32 multiplies in a flush class need the before-rounding model (finding 1). Until then the Vulkan class fails `scale_f32/denormals` and only that case.
- **Gates:** the Vulkan and D3D12 classes of this device differ exactly on fp32 arithmetic at or below 2^-126, as int-0001 decided; the selftests show everything else is identical.
- **Reopen** this decision if a validation-layer run (AP-3) reports a usage error, if a driver update changes the probe or the tininess words, or if the recipe changes section 6.3.

## Alternatives

- **A barrier after every dispatch,** as section 6.3 reads. Rejected: it serializes independent dispatches that the interface lets overlap, D1 does not do it, and the executor's barriers already order every dependent pair.
- **A barrier at the end of each list** instead of at its start. Equivalent for ordering, but a starting barrier also covers lists of other kinds (the backend's own uploads) without tracking what ran before.
- **A shared selftest module** in `Lrm.Gpu.Core`. Preferred, but `Lrm.Gpu.Core` is R4's; until the integrator moves it, the copy is checked byte for byte.
- **Hiding the tininess difference** by choosing selftest and conformance inputs away from 2^-126. Rejected: the difference is a property of the class, and the reports should show it.
