# ADR K1-0001: The basic kernels: fixed reduction trees, integer NaN tests and `precise` where CpuRef's rounding is the rule

- **Status:** proposed (K1, 2026-10-18), with the K1 pull request.
- **Owner:** K1.
- **Scope:** the seven kernels in `src/Lrm.Shaders/hlsl/kernels/basic/` (`embed_gather_bf16`, `rmsnorm_rows`, `rope_apply`, `silu_mul`, `add`, `copy_rows`, `argmax_rows`) and their conformance cases in `tests/Lrm.Kernels.Conformance/Cases/basic/`. It binds X1 (which dispatches them) and V1 (whose SPIR-V class runs the same bodies), and it records measured facts that I1's per-backend parity relies on.

## Context

The catalog entries of the seven kernels are frozen at contracts-v1 (KernelAbiAndCatalog): fields, thread counts and grids. Inside them, the kernels must:

- meet KernelBounds: `embed_gather_bf16`, `add`, `copy_rows` and the `argmax_rows` index bit-exact (`add` and `argmax_rows` in the class's measured fp32 denormal mode); `rmsnorm_rows`, `rope_apply` and `silu_mul` within the relative bound;
- be batch-invariant (BatchInvariance): a reduction's order depends only on its length;
- use no atomics, wave operations or 16-bit types, at most 32 KiB of groupshared, one body for DXIL and SPIR-V (ShaderBuildAndSourceConvention v1.1);
- finish every dispatch in under 100 ms for the Qwen3-0.6B shapes.

Two compiler facts shape the code. DXC marks DXIL float arithmetic `fast` (no `-Gis`, ADR int-0001), which allows reassociation, FMA contraction and the assumption that no value is NaN; so `v != v` is folded away. And SPIR-V declares no denormal mode, so a Vulkan class may flush where D3D12 preserves.

## Decision

1. **No catalog change.** Every kernel keeps its frozen entry. Element-wise kernels (`silu_mul`, `add`, `copy_rows`) run one thread per element at `LRM_GROUP_LINEAR(gid) * 256 + tid.x`; `embed_gather_bf16` uses its two-dimensional grid (`gid.x` a block of 256 columns, `gid.y` the row) and never folds; `rmsnorm_rows`, `rope_apply` and `argmax_rows` run one group per row at `LRM_GROUP_LINEAR(gid)`. Every kernel returns early when its group or thread has no work, judged from its own fields, so the extra groups of a folded grid write nothing.
2. **Row reductions use a fixed tree.** `rmsnorm_rows` and `argmax_rows` (256 threads) let thread t walk columns t, t + 256, ... in increasing order, then combine the 256 partials in groupshared with h = 128, 64, ..., 1 and a barrier after each step. The order depends only on `cols` and the catalog's thread count. Groupshared use is 1 KiB (`rmsnorm_rows`) and 3 KiB (`argmax_rows`), well under 32 KiB. A group whose row is out of range returns before its first barrier, as a whole.
3. **`rmsnorm_rows`** accumulates `mad(x, x, s)` per thread from +0, divides the tree's sum by `cols`, takes `rsqrt(mean + eps)` and writes `widen(w) * (x * r)`, CpuRef's element order. The sum's order differs from CpuRef's single sequential sum, so the kernel is judged by the relative bound, as the catalog says.
4. **`argmax_rows` tests NaN with integers.** A column is NaN when `(bits & 0x7FFFFFFF) > 0x7F800000`; a NaN never reaches a float comparison, and the row's flag is OR-ed through the tree, giving `0xFFFFFFFF`. A thread keeps its first maximum (it replaces only on `>`), and the tree takes the greater value or, on equal values, the lower index, so the result is the lowest index of the maximum whatever thread held it; +0 and -0 tie. The comparisons are `precise`, so DXIL has plain `fcmp ogt` and `fcmp oeq` without the fast-math flags: their `ninf` would let a driver assume no value is infinite, while ties of +inf and rows of -inf are part of the rule. They stay float comparisons, so a flushing class is *expected* to compare denormals as zero, as KernelBounds' flushed reference does. That is an assumption, not a measurement: the denormal probe measures arithmetic (`scale_f32`), and a device can flush arithmetic yet compare denormal operands exactly (Consequences, V1).
5. **`precise` where CpuRef's rounding is the rule.** `add`'s sum and `rope_apply`'s four products, difference and sum are `precise`. DXIL then has plain `fadd`, `fmul` and `fsub` (no `fast`), and SPIR-V gets `NoContraction` (the inspector accepts it): each operation rounds once, in the order of CpuRef's `Rows.add` and `Rows.ropeHead`, and no product is contracted into an FMA.
6. **`silu_mul` keeps every step in range, for every finite gate.** CpuRef's `g / (1 + exp(-g))`, written directly with the GPU's `exp` and fast division (the first version of this kernel), fails on valid gates: below g = -87.34 (ln 2^126) the denominator exceeds 2^126, where the RTX 4080's division returned 0 for results CpuRef F32 gives as normal floats; and DXIL's `exp(-g)` is `Exp(-g * log2 e)`, whose rounded product gives an error growing with |g| (about 1.2e-8 · |g| in relL2, over the 1e-6 floor below g = -80). So the kernel computes, with a = min(|g|, 120) and e = exp(-a) in (0, 1]:
   - s = g / (1 + e) for g ≥ +0, and s = (-a · e) / (1 + e) for g ≤ -0 (the same quotient, both sides multiplied by exp(g)); the denominator stays in [1, 2];
   - e by a Cody-Waite range reduction: n = round(-a · log2 e), r = (-a - n · C1) - n · C2 with C1 = 355/512 (nine significant bits, so n · C1 is exact for |n| ≤ 173) and C2 = ln 2 - C1 rounded (Cephes `expf`), then e = 2^n · exp(r) with |r| ≤ ln 2 / 2, so the GPU's `exp` only sees a small argument;
   - 2^n built from its bits as two normal powers 2^n1 · 2^n2 (n1 = floor(n / 2)), multiplied in after a · exp(r), so a · e keeps full precision where e alone would be a denormal; at a = 120, a · e < 2^-150, so every gate below -120 gives -0, as float32 silu does;
   - every float operation `precise`, so fast-math cannot fold C1 + C2 into ln 2 or reorder the products (without it, a gate of -3.4e38 also gave NaN with a random `up` but not with `up` = 1, as if the driver had formed g · up first);
   - non-finite gates as CpuRef: +inf gives +inf, -inf gives NaN, a NaN gate gives NaN (tested on the bits).

   Then y = s · up, CpuRef's last step. The result is not CpuRef F32's bits (it is judged by the relative bound); below g = -88.72, where CpuRef F32's `exp` overflows and it returns a signed zero, the kernel returns values close to CpuRef F64's (normal floats down to about g = -92, then denormals in a preserving class).
7. **Bit moves are integer-only.** `embed_gather_bf16` shifts the bf16 bits into the high half of a u32 and writes `0x7FC00000` for an id at or above `vocab`; `copy_rows` moves u32 words. No float instruction touches the data, so NaN payloads, signed zeros and denormals pass unchanged in every denormal mode.
8. **u32 index arithmetic.** Every element index is below its tensor's count, which one page (1 GiB) bounds by 2^28 four-byte or 2^29 bf16 elements, so the products of the kernel-abi.md minimum counts (`id * cols + c`, `row * cols`, `(row0 + r) * stride + c`) cannot wrap.
9. **The conformance cases** (`Cases/basic/BasicCases.fs`, 85 cases): the Qwen3-0.6B shapes at decode (T = 1) and prefill (T = 37 and 512), and edge shapes (one row or element, odd sizes, partial groups, outputs whose capacity exceeds the work, in-place aliases, folded grids, ties, NaN, denormals, every bf16 pattern). `silu_mul` also has one case per band of gates (`gates_m88p7_m87p4`, the same with `up` in [1e30, 1e31), `gates_m87p3_m80`, `gates_m80_m40`, `gates_m40_m8`, `gates_8_100` and `gates_m200_m88p8`), because relL2 over a case is dominated by its largest outputs: `wide_range` mixes the large negative gates with gates up to 100, and passed on the first kernel, which returned 0 for every gate in [-88.7, -87.4) (decision 6). The `rope_apply` cases read T_spec computed from the pinned `inv_freq` bits by CpuRef's exact trigonometry, checked at discovery against the ReferenceOracles hash `138c99b1…` and three entry vectors; positions the case does not use hold quiet NaNs, so a kernel that reads a wrong position fails. Six cases are `Case.gpuOnly`: the whole Qwen embedding table (151,936 × 1024 bf16, 311 MB), and folded grids of Qwen's shapes (k_norm of 8,193 tokens, q RoPE of 4,097 tokens, and `silu_mul`, `add` and `copy_rows` over 65,537 groups).
10. **The GPU-only cases are not built in the cpu tier** (`LRM_TEST_TIER=cpu`). CpuDevice never plans them (`Suites.casesFor`), but `HarnessTests`' arithmetic-model tests plan every discovered case on three CpuDevices at once; with these six cases the cpu tier of the conformance exe ran out of memory under an 8 GB GC heap limit (without a limit its working set peaked at 26.9 GB). Without them it passes under a 4 GB limit (peak 3.3 GB, 11 s). The gate goes when those tests filter GPU-only cases as `Suites.casesFor` does (request to E1).

- **Timing.** Dispatch times are the faster of two runs with the GPU's own timestamps, taken while the harness uploads and checks between dispatches, so the GPU mostly sits at low clocks (it idles at P8: 210 MHz SM, 405 MHz memory) and its residency state varies with the session's 942 MiB heap. - **Decode.** At the decode shapes every K1 dispatch takes 2 to 5 µs except `argmax_rows` over the 151,936 logits, which takes 97 µs, and 101 µs for 37 rows. So it is latency-bound on one group of 256 threads (the frozen grid is `rows`). The review measured 92 µs before the compares were `precise`; at these clocks the two are the same.

**Disassembly** (pinned DXC, the build's flags, `-Fc`): `add`, `rope_apply` and `silu_mul` have no `fast` flag on their arithmetic. `silu_mul` has plain `fmul`, `fsub`, `fadd` and `fdiv`, `Round_ne` and `FMin`, and its `Exp` takes r · log2 e only; 2^n1 and 2^n2 are built with `shl` and `add`. `argmax_rows` tests NaN with `and i32 %x, 2147483647` and `icmp ugt i32 ..., 2139095040`, and its 17 float compares are plain `fcmp ogt` and `fcmp oeq`. `rmsnorm_rows` has `FMad` and `Rsqrt`. In SPIR-V, `rope_apply` carries six `NoContraction` decorations, `silu_mul` eighteen and `add` one; SPIR-V compares carry no fast-math flags.

## Consequences

- **V1:** the SPIR-V blobs of these kernels pass the inspector, but no Vulkan device has run them. V1 runs the same cases through the harness, and K1's "both backends" gate stays open until then (wave 3). If V1's class measures `flush`, `add` and `argmax_rows` are compared in that mode by the harness, and the relative kernels get KernelBounds' flushed allowance.
  - V1 checks `argmax_rows/denormal_max` on its class specifically. In a flushing class the reference expects index 5 in row 0 (the denormal at 10 ties +0 at 5), which holds only if the device's float compares flush as its arithmetic does (decision 4).
  - If they do not, `argmax_rows` must flush its inputs explicitly in that class: an integer test for `0 < |bits| < 0x00800000` sets the value to a signed zero. That needs the class's mode in the kernel's arguments, so it is a KernelAbiAndCatalog contract change. The other way out is for KernelBounds to record the class as `mixed` for `argmax_rows`.
- **X1:** `embed_gather_bf16` takes at most 65,535 rows per dispatch (grid y), so a longer prefill is split. `rope_apply` reads the Rope arena's table at `pos0 + row / heads`. `argmax_rows` returns `0xFFFFFFFF` for a row with a NaN, which the host turns into CpuRef's error. `silu_mul` turns a NaN gate into a NaN.
- **X1 and I1, decode latency:** `argmax_rows` is the slowest K1 dispatch of every decoded token: about 0.1 ms, against 2 to 5 µs for the others (Evidence), because one group reduces the whole vocabulary. That is far inside the 100 ms budget. If decode latency matters later, a two-pass argmax (per-block partials, then one reduction per row) is an additive catalog kernel, through a contract-change PR.
- **E1:** the request in decision 10.
- **Reopen** if a backend's class fails one of these cases, if `-Gis` is adopted for DXIL (decision 5 would then be the default), if a driver update changes the measured errors, or if V1's class compares denormals differently from how it computes with them.

## Alternatives

- **A sequential sum per row in one thread** for `rmsnorm_rows` would match CpuRef's order exactly, but leaves 255 of 256 threads idle; the relative bound is the rule for this kernel, and the tree is more accurate.
- **Integer ordering keys for `argmax_rows`** (comparing sign-adjusted bits) avoid float compares entirely, but rank -0 below +0 and a denormal above zero in a flushing class, so they would disagree with CpuRef's tie rule and with the flushed reference.
- **CpuRef's formula with the GPU's own `exp` and division for `silu_mul`** (`g / (1 + exp(-g))`, the first version) takes three instructions, and its error was a twentieth of the bound on gates in [-8, 8]. But it returned 0 below g = -87.34, and its error passed the floor below g = -80 (Evidence). Clamping the gate instead would be wrong for the same gates, since CpuRef F32 gives normal results down to g = -88.72.
- **A polynomial `exp`** for `silu_mul` would not depend on the GPU's `Exp` at all. But the range reduction alone already brings every band to the error of a small argument, and `Exp` is what both backends provide.
- **`-Gis` for the whole DXIL set** would remove fast-math everywhere, but it changes every DXIL blob and the ShaderSetHash, a ShaderBuildAndSourceConvention contract-change (ADR int-0001, decision 5). `precise` gives the same rounding to the three kernels that need it, and plain compares to `argmax_rows`.
